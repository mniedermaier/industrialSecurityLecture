\textbf{Exercise 6.2 -- Diamond Model (Industroyer2, April~2022).}
\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{Adversary:} Sandworm / ELECTRUM (GRU Unit~74455), the cluster behind the
        Industroyer lineage; same lineage as 2016 CrashOverride.
  \item \textbf{Capability:} Industroyer2 -- a single statically-configured IEC~60870-5-104
        payload (vs.\ the modular 2016 build) deployed alongside CaddyWiper for cleanup;
        techniques \texttt{T0855}, \texttt{T0816}, \texttt{T0826} from Ex.~6.1.
  \item \textbf{Infrastructure:} adversary tooling staged on internal hosts inside the
        victim's own environment (largely \emph{Type~2}: living off victim infrastructure)
        rather than chatty external C2; minimal external footprint by design.
  \item \textbf{Victim:} a Ukrainian \emph{electric transmission} utility; asset class =
        substation RTUs/relays; the consequence reached for = \emph{loss of control} of
        breakers and \emph{loss of availability} (de-energisation) of high-voltage substations.
  \item \textbf{Meta:} April~2022; scheduled execution attempt thwarted before mass impact;
        ICS Cyber Kill Chain \textbf{Stage~2} (the actor already had OT access and was acting on
        the physical process). \textbf{Confidence: high} on capability and victim (vendor
        forensic samples + named utility via CERT-UA/ESET); \textbf{moderate} on the precise
        operator sub-cluster -- attribution rests on tooling lineage, which a different
        operator could in principle reuse.
\end{itemize}
\textbf{Left unknown:} the exact \emph{initial-access} vector for this specific 2022 intrusion
was not fully public at disclosure time; recorded as ``unknown -- likely earlier IT
compromise''. One new data point (a confirmed initial-access artefact tied to a known Sandworm
loader) would raise operator-cluster confidence from moderate to high.\\[2pt]
\emph{Sources:} ESET + CERT-UA \emph{Industroyer2}, April~2022; Dragos ELECTRUM page.
\end{solutionbox}

\begin{solutionbox}
\textbf{Exercise 6.4 -- Consequence-driven PIRs (electric transmission vs.\ ELECTRUM).}\\[2pt]
\begin{enumerate}\setlength{\itemsep}{1pt}
  \item \textbf{PIR-1:} Is ELECTRUM developing or deploying capability against the IEC~104 /
        IEC~61850 stacks or relay families we operate? \emph{Consequence:} loss of control of
        breakers. \emph{Source:} CISA/CERT-UA advisories + relay-vendor PSIRT.
        \emph{Trigger:} any advisory naming our protocol/relay family.
  \item \textbf{PIR-2:} Are there new External Remote Services / valid-account footholds into
        our OT segment? \emph{Consequence:} the IT$\to$OT pivot enabling Stage~2.
        \emph{Source:} OT remote-access logs, EDR on jump hosts. \emph{Trigger:} any OT-segment
        logon outside the change window.
  \item \textbf{PIR-3:} Is wiper/cleanup tooling (CaddyWiper-class) co-deployed in current
        campaigns? \emph{Consequence:} loss of view + impeded recovery. \emph{Source:} Dragos /
        Mandiant intel + our EDR. \emph{Trigger:} wiper IOCs or destructive-cmd patterns.
  \item \textbf{PIR-4:} Are our exposed/edge OT-adjacent devices being scanned or accessed?
        \emph{Consequence:} initial access. \emph{Source:} perimeter and honeypot telemetry.
        \emph{Trigger:} sustained scanning of our public ranges hitting OT-adjacent services.
  \item \textbf{PIR-5:} What is the strategic tempo -- does geopolitical escalation correlate
        with grid targeting? \emph{Consequence:} timing of likely action. \emph{Source:}
        government/E-ISAC strategic reporting. \emph{Trigger:} sector-wide alerting level rises.
\end{enumerate}
\textbf{Ranking justification:} PIRs are ordered by \emph{proximity to irreversible process
consequence} -- PIR-1/2 sit at loss-of-control and the Stage-2 pivot (highest, most
time-critical), while PIR-5 is strategic context that shapes posture but does not by itself
trigger an operational response. \emph{Marking:} each PIR must be a question anchored to a
\emph{process} consequence; any PIR that drifts to a generic IT outcome (``are we patched?'')
loses the mark.
\end{solutionbox}

\begin{solutionbox}
\textbf{Exercise 6.5 -- TTP$\to$detection (T0855 Unauthorized Command Message).}\\
A Zeek-based notice for anomalous IEC~104 / Modbus write/command bursts from a non-EWS host:
\begin{lstlisting}[language=python]
# zeek: command-message bursts on OT control protocols (ATT&CK ICS T0855)
# telemetry: zeek modbus.log / dnp3.log / iec104 analyzer output
@load base/protocols/conn
const ews_hosts: set[addr] = { 10.20.0.10 } &redef;  # known engineering WS
const write_fcodes: set[count] = { 5, 6, 15, 16 };   # Modbus writes
global cmd_count: table[addr] of count &create_expire = 10sec &default = 0;

event modbus_message(c: connection, hdr: ModbusHeaders, is_orig: bool) {
  if (is_orig && hdr$function in write_fcodes && c$id$orig_h !in ews_hosts) {
    cmd_count[c$id$orig_h] += 1;
    if (cmd_count[c$id$orig_h] > 20)            # >20 writes / 10s window
      NOTICE([$note=OT::Unauthorized_Command_T0855,
              $conn=c, $msg="T0855: command burst from non-EWS host"]);
  }
}
\end{lstlisting}
\textbf{Logic:} count write/command function codes per source over a 10\,s window; alert when a
\emph{non-engineering} host exceeds 20. \textbf{False positive:} a commissioning/batch write
from a legitimate HMI or a newly added EWS. \textbf{Tuning:} maintain \texttt{ews\_hosts} as an
allowlist and suppress during scheduled change windows -- this narrows scope without blinding
the rule to off-window writes (the actual threat). \textbf{Pyramid of Pain:} this is a
\emph{TTP-level} detection (apex); to evade it the adversary must avoid command-message bursts
entirely (slow, single-shot writes) or impersonate an EWS source -- both costly and noisy.
\emph{Marking:} accept any syntactically plausible Sigma/Zeek rule carrying its \texttt{Txxxx}
tag, a stated FP, and a tuning note that does not disable the detection.
\end{solutionbox}

\begin{solutionbox}
\textbf{Exercise 6.6 -- Critiquing the over-attribution claim.}\\
Four distinct errors:
\begin{enumerate}\setlength{\itemsep}{1pt}
  \item \textbf{Shared-TTP / base-rate error.} \texttt{netsh portproxy} and Modbus writes are
        \emph{generic} -- used by many actors and by legitimate admins. Common TTPs are not
        identifying. \emph{Correction:} attribution needs distinctive, corroborated tradecraft,
        not shared techniques.
  \item \textbf{Wrong Pyramid level for attribution.} Behaviours this low/common cannot carry
        named-actor attribution; the analyst is over-reading a TTP. \emph{Correction:} treat
        the TTP as a \emph{detection} signal, not an attribution signal.
  \item \textbf{Missing IT$\to$OT distinction.} \texttt{portproxy} on a jump box (IT,
        \texttt{T1090}-class) and a Modbus burst (OT, \texttt{T0855}) are two separate facts;
        the claim fuses them into one story without showing the pivot. \emph{Correction:}
        separate the IT and OT observations and state whether a pivot was actually observed.
  \item \textbf{Uncalibrated confidence + wrong consumer.} ``This is Volt Typhoon... notify the
        board'' jumps to certainty and escalates raw, single-source observations to the wrong
        audience. \emph{Correction:} use estimative language, state confidence, and route to the
        SOC for triage first.
\end{enumerate}
\textbf{Defensible rewrite:} ``We observed write-command bursts on TCP/502 from a non-EWS host
and a \texttt{netsh portproxy} on a jump box; this is anomalous and warrants OT-segment triage,
but the TTPs are not actor-specific, so attribution to any named group is \emph{unlikely to be
supportable} without further evidence.''
\end{solutionbox}

\textbf{Exercise 6.7 -- TLP-marked one-paragraph assessment (model answer).}\\
\textbf{TLP:GREEN.} \emph{Bottom line:} we assess it is \textbf{likely} (moderate confidence)
that ELECTRUM-class capability against IEC~104 grid devices remains active in our sector,
based on public ESET/CERT-UA reporting of Industroyer2 and Dragos ELECTRUM tracking. The two
TTPs that matter most this week are unauthorized command messages on OT control protocols
(\texttt{T0855}) and reuse of external remote-access into the OT segment (\texttt{T0822}); both
are detectable with telemetry we already hold. \textbf{Recommended action (priority~1):} deploy
the non-EWS command-burst notice on our IEC~104/Modbus segments and review all OT-segment
remote logons against the change calendar, because the consequence we are protecting against is
loss of control of breakers. Confidence is moderate, not high, because our judgement rests on
sector-level reporting rather than direct observation in our own estate.\\[3pt]
\emph{TLP justification:} the inputs are public (TLP:CLEAR), but the synthesis ties named TTPs
to \emph{our} detections and posture, so it is shared within the cohort/peer community as
\textbf{TLP:GREEN} -- not posted publicly (that would be CLEAR) and not restricted to named
recipients only (AMBER/AMBER+STRICT), which the cohort-wide audience does not require.
\end{solutionbox}

\begin{warnbox}
\textbf{TLP handling.} The marking is set by the \emph{most restrictive} input plus the
intended audience -- you cannot downgrade a source. Public reporting is TLP:CLEAR; a
peer/cohort product is typically TLP:GREEN; anything tying named indicators to a specific
victim or pulled from an ISAC/paid feed defaults to TLP:AMBER and is \emph{not} redistributable.
Re-broadcasting AMBER material publicly, or stripping a marking off inherited content, ends your
access to the source and may breach the originator's caveats. When unsure, mark up
(AMBER+STRICT), not down.
\end{warnbox}

\begin{solutionbox}
\textbf{Exercise 6.8 -- Essay marking rubric (6~points).}
\begin{enumerate}\setlength{\itemsep}{1pt}
  \item \textbf{Pyramid argument} (1~pt). Explains that LotL actors leave hashes/IPs/domains --
        the cheapest, most volatile layer -- and that signed Windows binaries plus Type-2
        hijacked SOHO routers defeat hash- and IP-feeds by construction.
  \item \textbf{Detection classes that work} (1~pt). Names behavioural (parent--child trees,
        e.g.\ \texttt{w3wp.exe}$\to$\texttt{cmd}$\to$\texttt{ntdsutil}), identity/UEBA
        (anomalous service-account logons, Kerberoasting), and command-line analytics, with one
        concrete example each.
  \item \textbf{OT-specific twist} (1~pt). Recognises that IT-side process/identity analytics do
        not transfer to Purdue L1/L2, and names the OT telemetry needed there -- protocol
        baselining (Zeek modbus/iec104), command-message anomaly detection, and asset/flow
        whitelisting -- because L1/L2 has no EDR.
  \item \textbf{Honest limitation} (1~pt). Behavioural detection costs a baseline, carries
        false-positive load, and has latency / tuning burden; a steelmanned drawback, not a
        throwaway.
  \item \textbf{Primary source} (1~pt). Cites CISA \emph{AA24-038A} (7~Feb~2024), Microsoft
        Volt Typhoon (May~2023), or Dragos VOLTZITE reporting -- no invented sources.
  \item \textbf{Writing, calibration, structure} (1~pt). Estimative language where it makes a
        judgement; no overclaiming attribution from shared TTPs.
\end{enumerate}
\emph{Exemplar thesis:} indicator feeds detect the cheapest layer of an actor whose entire
design is to operate without that layer; the durable defence climbs the Pyramid to behaviour,
identity, and -- in OT -- protocol baselining, accepting higher baseline and false-positive cost
as the price of catching a LotL adversary at all.
\end{solutionbox}
